xp5_nova_fpgademo -- nova_fb demos written as real C, compiled through
nova-llvm-backend, instead of hand-assembled octal
================================================================================

WHAT THIS IS
------------
sourcedir/nova_fb/ has a real FPGA-framebuffer-mock device (device 042) for
the SimH Nova, and its own demos (demo/*.ini) are generated by small
Python-hosted two-pass Nova assemblers (gen_cursor.py, gen_modeswitch.py,
gen_fractal.py) -- hand-picked mnemonics and PC-relative displacements,
because there was no C compiler for the Nova in this repo.

sourcedir/cully_llvm/ changed that: it wired up cullyrichard's
nova-llvm-backend, a genuine clang/LLVM frontend and Nova backend
(https://github.com/cullyrichard/nova-llvm-backend), and proved it against
this repo's own real Nova SIMH with a 218-test C89 conformance battery.

This directory is what that toolchain is actually FOR, applied to nova_fb:
demos written as ordinary C, driving the framebuffer card's IOT bus with
nothing but `asm volatile("DOA/DOB/DOC/NIOP ...")` -- the exact idiom
cully_llvm's own runtime (rt/eclipse_rt.c's putchar/getchar) already uses for
the console (device 011), pointed at device 042 instead. No hand-picked
octal, no manual PC-relative arithmetic: clang and llc do that, the same way
they would for any other freestanding target.


WHAT IS IN THIS DIRECTORY
--------------------------
  src/fractal.c            demo 1: a title card (nova_fb char mode, built-in
                            ROM) then a continuously scrolling AND fractal
                            (Sierpinski gasket) -- see its own header comment
  gen_fractal.py            builds gen/fractal.ini from src/fractal.c
  verify_fractal.py         recomputes the title card and sampled scroll
                            frames independently and diffs every pixel --
                            same technique as ../nova_fb/verify_fractal.py
  __testlist__vga_fractal_fb.py
                            flask entry, "xp5_nova_fpgademo" / vga_fractal_fb

  src/malloctest.c          demo 2: a malloc/free/calloc tester for this
                            platform's runtime allocator -- probes the heap's
                            real capacity, confirms free() doesn't reclaim,
                            demonstrates calloc's nmemb*size overflow and the
                            allocator's own bounds-check integer-overflow
                            bypass, all shown live on the card as a memory
                            layout grid + rotating status log. Halts with a
                            "MALLOCTEST: PASS"/"FAIL" verdict -- see its own
                            (long) header comment for the full reasoning.
  gen_malloctest.py          builds gen/malloctest.ini from src/malloctest.c
  verify_malloctest.py       OCR-decodes the final frame (via the shipped
                            character ROM) and diffs it against a
                            byte-for-byte Python replay of main()'s own
                            fb_puts/mark_range/log_line calls -- fully
                            deterministic, unlike fractal.c's evolving scroll

  src/cuberotate.c          demo 3: a rotating wireframe cube, perspective-
                            projected with 16-bit fixed-point arithmetic (no
                            libm, no FPU -- an earlier float version didn't
                            fit, see below), RTC-paced (device 014, 60Hz)
                            with a frametime readout recomputed every 5 real
                            seconds in the corner -- see its own header
                            comment for the fixed-point scaling and the
                            timer programming model.
  gen_cuberotate.py          builds gen/cuberotate.ini from src/cuberotate.c
  verify_cuberotate.py       recomputes the wireframe exactly (same
                            fixed-point arithmetic, mirrored by hand) since
                            ax/ay advance deterministically every frame; the
                            frametime corner is genuinely wall-clock-
                            dependent so it's only OCR'd for plausibility,
                            not asserted to an exact value
  __testlist__vga_cuberotate.py
                            flask entry, "xp5_nova_fpgademo" / vga_cuberotate

  gen/*.ini                 committed build output, like cully_llvm's own gen/
  output/                   PNGs land here (gitignored, like nova_fb's own)

  All three gen_*.py scripts share the same nova-cc invocation shape; see
  gen_fractal.py's own header comment for the one difference that matters
  (fractal.c and cuberotate.c never halt, so their .ini has no "quit" after
  "go 100" -- malloctest.c halts on its own, so gen_malloctest.py's .ini
  does).


BUILDING gen/fractal.ini
-------------------------
Requires ../cully_llvm/_toolchain/ already built -- see ../cully_llvm/NOTES.txt
for the full clang+dgasm build (~3.6GB, gitignored, ~15-90 min). Once that
exists:

    python3 gen_fractal.py

Regenerate this any time src/fractal.c changes; gen/fractal.ini is committed
so a testlist run never has to invoke the toolchain live (same convention as
cully_llvm's own gen/*.ini).


RUNNING IT DIRECTLY
--------------------
There is no simulator build in THIS directory -- the framebuffer device only
exists in ../nova_fb/bin/dgnova-fb, so that is what runs gen/fractal.ini too
(the shared, un-forked dgnova has no device 042, same reason every nova_fb
testlist points "binary" at that build instead):

    cd /testsrc/sourcedir/xp5_nova_fpgademo
    timeout 5 ../nova_fb/bin/dgnova-fb gen/fractal.ini

It never halts (main()'s outer loop has no exit -- see src/fractal.c), so a
bare run needs `timeout` or a manual Ctrl-C; the testlist manages this with
test_wait_for_seconds + test_terminate_all instead.


A REAL BUG THIS CAUGHT, ON THE FIRST BUILD
--------------------------------------------
The very first compile succeeded cleanly (one harmless "return type of
'main' is not 'int'" warning) and ran without crashing, but
verify_fractal.py found 77 mismatched pixels in the title card. Not a
toolchain bug: two of the title strings were one line too long for the
card's 32-column text mode, and the C loop that writes each character had no
bounds check on `col` -- so the tail of an overlong line wrapped straight
into the NEXT row's first few cells (TEXTBUF + row*COLS + col computes a
perfectly valid address there, the card has no idea a "line" was ever meant
to stop at column 32). Fixed two ways: shortened the offending strings to
fit, and added `col < COLS` to the write loop's condition so a future
overlong string fails by silently truncating instead of corrupting whatever
row comes next. See src/fractal.c's TITLE array and its write loop.


WHAT malloctest.c ACTUALLY FOUND
----------------------------------
Reading ../cully_llvm/_toolchain/nova-llvm-backend/nova-toolchain/rt/eclipse_rt.c's
allocator directly (it's ~20 lines, quoted in src/malloctest.c's own header)
turned up two real, reproducible weak points before a single test even ran:

  * calloc(nmemb, size) computes nmemb*size as a plain 16-bit unsigned
    multiply with NO overflow check. calloc(4096, 4096) -- nominally 16MB,
    impossible on this machine -- silently becomes calloc(*, 0) because
    4096*4096 mod 65536 == 0, and succeeds. A caller trusting the return
    value writes into a buffer it believes is 16MB and is actually 0 bytes.

  * The allocator's own guard, `if (heap_used + size > HEAP_WORDS) return 0`,
    is the identical class of bug: heap_used and size are both plain
    unsigned int, so a size chosen as (0 - heap_used) (well-defined unsigned
    wraparound) makes heap_used+size wrap to exactly 0, which is never
    greater than HEAP_WORDS. The guard that is supposed to reject "this
    doesn't fit" can be made to pass for ANY current heap_used, and the
    internal bump pointer wraps to 0 right along with it -- reproduced
    safely in this test by showing the very next ordinary allocation lands
    on the SAME address as an earlier live one, not by writing out of
    bounds to prove it.

Both are exactly the "allocating over program structure" class of weak
point the platform was suspected to have, and both were found by reading
~20 lines of the actual allocator, not by guessing -- src/malloctest.c's
header comment has the full derivation, including the arithmetic that says
exactly which two pointers must collide and why.


WHAT cuberotate.c ACTUALLY HIT
---------------------------------
Three real, distinct backend/toolchain limits, found empirically while
building this one demo (in order of how they were hit):

  * A variable-count shift (`bits >> (2 - col)`, in the font blitter)
    crashed llc outright: "Eclipse backend only supports shifts by a
    compile-time constant amount". Fixed by indexing a 3-entry mask table
    instead of shifting -- see draw_char's COLMASK comment.

  * The first version of the rotation/projection math used `float`
    throughout. It compiled and ran, but dgasm failed with page after page
    of "Address out of range... should be 0-255" across the soft-float
    runtime's own statics (sf_add_*, sf_mul_*, sf_div_*, u32_*) -- the
    runtime's own comment in eclipse_rt.c/stdio.h says float support is
    NOT free (a large, fixed page-zero cost), and this program's own
    fairly ordinary set of globals (vertex/edge tables, a sin table, a
    font table) was enough to blow the shared 256-word budget once float's
    cost was added on top. Rewritten with 16-bit fixed-point integers
    instead (see the file's own header for the exact scaling), which pulls
    in none of the soft-float runtime.

  * A `struct { char c; unsigned char rows[5]; }` array, indexed as
    `FONT[gi].rows[row]`, reproducibly read back the WRONG glyph row --
    confirmed with an isolated standalone test with no cube or timer code
    at all, so this is a genuine backend bug in struct-array-of-arrays
    field access, not a font-data or drawing-math mistake. Two parallel
    flat arrays (`FONT_CHARS[13]`, `FONT_ROWS[13][5]`) sidestep it and were
    verified correct with the same isolated test.

A fourth bug was in verify_cuberotate.py itself, not the toolchain: its
first version's `fmul` reimplemented C's `/` (truncate toward zero) where
the actual C code uses `>>` (which floors toward -infinity for a negative
operand -- Python's native `>>` already does this correctly). The two only
agree when every operand happens to be non-negative, which is why it
passed at ax=ay=0 and failed by hundreds of pixels at other angles --
found by diffing the recompute against a real run's PNG at a failing
angle and noticing want/got were nearly equal in COUNT but not in
membership, the signature of a systematic off-by-a-sign-convention rather
than a missing/extra feature.


WHY A SEPARATE PARENT CONTAINER, NOT ../nova_fb's
---------------------------------------------------
../nova_fb's own "nova fb sprite cursor" parent groups every DEMO for that
card, all built the same (hand-assembled) way. This one groups demos built a
different way (real C through a real compiler) for the same card -- the two
pipelines are independent, same relationship
cully_llvm/../nova_ctestsuite/nova_c already have for the plain C89 suite
(one parent per toolchain, not per device).
